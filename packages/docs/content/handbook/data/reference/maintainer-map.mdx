## Trace a query update

The owner publishes permitted records and membership evidence. A tab applies that publication to its local read model and projects the queries its components use. The owner uses the same projection rules when deciding what information is still missing. Feature code does not manage either copy.

For an existing query, Vem retains each record's contribution: whether it matches, its displayed values, and its missing requirements. A record update recalculates that record's contribution. Unchanged records reuse their previous calculations. Custom scope and filter functions are evaluated again for a changed record; Vem does not assume that these functions read only selected fields.

Before projection, an ordinary observation recalculates currency for changed facts and facts whose evidence depends on them. The dependency index carries changes through derived facts and relationships; it does not treat a new value as evidence that unrelated facts changed. Access changes and event-continuity changes can require broader checks.

This saves repeated evaluation of every resource when one resource changes. Assembling a changed result can still depend on its row count. It is not a constant-time guarantee for every publication.

Access and membership changes can affect which records belong or may be disclosed, so they require broader recomputation. Initial attachment, reset, or a query falling behind the bounded change history can also rebuild its projection. These paths preserve the same results as a full calculation. Inactive retained queries do not perform notification work; reading them again catches up to the current model.

Start with `src/read-model/query-projector.ts` for query contributions, `src/read-model/projection.ts` for the tab's local model, and `src/runtime/read-model-export.ts` plus `src/read-model/publication.ts` for publication changes. Follow the behavior tests in `tests/host` and `tests/queries` before changing their bookkeeping.

## Measure the right work

Run from the repository root:

```sh
node --import tsx scripts/benchmarks/data-publication.mjs 100 1000 5000
node --import tsx scripts/benchmarks/publication-pipeline.mjs 100 1000 5000
```

The first isolates owner observation without active owner queries and tab projection. The second includes active owner queries and three simulated tabs, measuring delta preparation, structured cloning, replica application, and subscriber reads separately. It checks selected-field updates, movement between filters, and updates outside some selections.

These are CPU benchmarks with deterministic data. Their sum is not browser interaction latency: actual Worker scheduling, network, React, and rendering are excluded. Use a browser profile to assess those parts, and behavioral tests to assert which records are evaluated rather than machine-specific timing limits. `packages/data/tests/README.md` documents the benchmark settings and comparison options.
