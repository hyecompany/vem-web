A feature test should prove what a person sees and can do. `createTestClient` supplies the same provider contract as the application, using named queries, commands, and edits.

## Change the situation while the view is open

<Example file="feature-guide/testing.tsx" region="transition" />

Call `showFailure(fixture)` after rendering. Assert that the known task remains visible and the source error is shown. Use `setQuery` to supply another result; `replace` lists fields whose old values must be removed when intentionally switching to a partial scenario.

Fixtures match query descriptions. If a test changes the filter, supply a fixture for that filtered query too, or establish sufficient known information for the runtime to answer it.

Assert that the textarea and its value disappear. For write-only loss, use `setEditAccess(edit, { write: "denied" })` and assert that Save is disabled while readable input stays.

## Choose the boundary to test

| Change | Useful check |
| --- | --- |
| A field or filter | Type-check selected fields; render missing values |
| A command | Admission, progress, and command-specific outcomes |
| An editor | Dirty external change, conflict, and access loss |
| A domain definition | Real backend responses, events, and replacement boundaries |
| A browser host | Actual worker ownership, two tabs, and storage failures |

Feature fixtures exercise the runtime's consumer behavior, not HTTP, IndexedDB, or worker ownership. Those belong in integration tests. For manual exploration inside an application, see [development tools](/docs/data/connect/devtools).
