**Vem chooses the reads. You describe what each source can provide.** There is no planner to write for a screen, resource, or combination of tabs.

A source is one supported way to read your backend: a URL list, a summary collection, one full record, a filtered search, or a page. It declares what information that read can establish and how to execute it.

## Plan for the whole application

The shared owner combines the currently outstanding query requirements it knows about, from every connected tab and imperative reader. It subtracts permitted information already known, expands prerequisites for derived fields, and compares combinations of available sources. Work already in flight can satisfy overlapping demand without another request. Later arrivals can reuse that work and its results; Vem does not predict requests from a tab that has not asked yet.

The browser client groups subscriptions and reads made in the same synchronous turn before handing them to the owner. A set of newly mounted rows can therefore participate in one planning decision. Render permitted stale rows while they revalidate: their mounted consumers add their field requirements immediately. This also works after restart once the host identifies the same caller and saved permissions resume; no consumer history or fetch hints are needed.

For example, four task details might be cheaper as one collection read. If three details are already known, one detail read might be cheaper. If another tab also needs collection membership, that changes the comparison again. No component chooses an endpoint.

## Choose using available evidence

Vem compares combinations of reads for the outstanding requirements. Its default policy prefers bounded acquisition, then the smallest total response across the chosen reads. When totals match, it favors fewer requests, then less information outside the current requirements. Response size counts returned identities and advertised values, including duplicates across requests; it does not estimate bytes, latency, or server processing.

| Outstanding need | Default choice | Reason |
| --- | --- | --- |
| Descriptions for all 5 known tasks | Collection | The same five representations in one request |
| Descriptions for 3 of 40 known tasks | Details | Avoid returning 37 unrelated representations |
| Names with no known inventory | Name list | Establish the choices using the narrower representation |
| Several known task details, unknown collection size | Details | Their response size is bounded; the full collection's is not |

The planner considers all consumers together. A list needing 500 names does not also need 500 descriptions: visible rows add those requirements separately. In a filtered list, display fields are needed only for established matches; an unresolved candidate first needs evidence that decides whether it belongs. Already-known descriptions need no read, and shared responses can avoid duplicating fields across requests. Another view asking for membership or fields can therefore change the choice; there is no fixed “fetch the collection after three rows” threshold.

Population information comes from permitted knowledge for the source's actual scope and supported filter:

- **Known:** the observed inventory establishes the number of matches.
- **Bounded:** a complete inventory is available, but some candidates cannot yet be matched against the filter.
- **Unknown:** incomplete information supplies no upper bound.

A retained complete inventory remains useful after an event gap or restart. Its count is historical planning evidence, not a guarantee about the current collection. Vem does not substitute an invented population when information is missing. A partial inventory cannot establish an upper bound, and withdrawn knowledge cannot support the estimate. None of these estimates creates presentation rows or proves current completeness.

Planning uses a bounded search and keeps the best combination it finds. This policy reduces avoidable reads without claiming a universally optimal plan for unknown backends.

## Cooperate with browser scheduling

Vem starts independent selected reads without a default concurrency ceiling. It still combines overlapping demand before dispatch and respects dependencies. The browser manages connections and HTTP multiplexing; Vem does not assume six available connections.

A source receives a derived `context.fetchPriority`: missing information uses `high`, while revalidation supported by readable stale evidence uses `low`. Shared work takes the strongest demand, and prerequisites inherit the need they unlock. Sources without classified demand use `auto`. Pass the hint through your shared transport to `fetch(url, { signal: context.signal, priority: context.fetchPriority })`; screens do not declare priorities. Preparing an editor uses `high`.

These are browser hints, not ordering guarantees. New consumers can change the hint for subsequent page requests, but Vem does not cancel and repeat a request to change a priority already submitted. An optional host `maxConcurrent` can constrain specific backends; its waiting work retains arrival order. Command admission has separate limits.

Once replacement reads are running, Vem aborts a redundant read only when the selected replacements cover every remaining requirement it serves across consumers. Scope, filters, freshness, and representation-specific fields still matter: a collection response cannot replace a detail-only ETag. Canceled reads cannot publish late results, and a failed or partial replacement can fall back to the canceled source. This stops browser observation and transfer; it cannot guarantee that the server stopped processing the request.

Transport deadlines include time waiting for the browser to obtain a connection and receive the response. Fetch does not expose a socket-assignment event that can safely start a server-only timer. Choose an end-to-end deadline for the application, preserve readable content if it expires, and let the query report failure and offer retry. A timeout alone establishes neither server processing time nor loss of permission.

## Which characteristics belong in the definition?

| Capability | What Vem uses it for |
| --- | --- |
| `fields`, `relationships` | Identify which missing facts or links a read can supply |
| `membership` | Distinguish enumeration from details about already known records |
| `scope` | Keep tenant, project, or other collection boundaries separate |
| `filters` | Push compatible predicates to the backend; evaluate remaining requirements locally |
| `select: true` | Request only missing fields when the backend supports field selection |
| `cost` | Optionally supply a justified, comparable backend work model |
| `pagination` | Follow bounded continuation without claiming an early page is complete |
| `access`, `accessUnknown` | Admit reads according to current authority before dispatch |
| `available` | Exclude a representation the backend does not support |

By default a source returns a fixed representation. With `select: true`, `request.fields` is the requested projection. Vem cannot expand a request already sent; a later field may require additional work. A fixed representation already in flight can serve any of its declared fields.

A URL, response header, or nested reference can establish facts too. Extract and advertise those facts when the backend semantics justify them. A URL containing a task ID may establish that ID; it does not establish permission, notes, or a writable representation's ETag.

## Support backend filters

A feature's [text query](/docs/data/build/display#filter-text) describes its intended matches. To let Vem use a backend search endpoint, assign its supported semantics to the source's `filters`:

<Example file="integration/filters.ts" region="capabilities" />

Use `filters: taskSearchFilters` on that source. Vem normalizes a feature's `where` object into a predicate before planning. `run` receives the supported predicate in `request.where`; your transport encodes it in the backend's syntax. `isFilterExpression` distinguishes that normalized expression from an equality map. Expressions expose `$filter`, with `field` and `value` on leaves, `comparison` on text leaves, and `conditions` on `all`/`any` groups. Feature code uses `where` objects; only source adapters need this representation.

Declare only behavior the backend actually supports. The `text` combinations must match exactly; a case-insensitive query cannot use a case-sensitive backend search. Omit `text` when the source cannot search substrings. An optional pure `supports(expression, context)` can further restrict supported grouping or server capabilities. The existing `filters: ["status"]` shorthand declares equality support only.

An OR (`any`) needs support for **all its branches** before Vem can send it to that source. Searching titles alone would lose tasks matching only notes. Unsupported predicates therefore use broader reads and local evaluation; an AND (`all`) may still use supported conditions to narrow those reads safely. If no source can supply enough evidence, the result settles with unresolved candidates instead of inventing matches.

A source can return only matching URLs or identities. Report those identities as membership for the **actual predicate sent**, with the actual scope and completeness. This proves that each returned task matched the whole expression; it does not reveal which OR branch matched or invent the text of its notes.

Equality can prove more: membership for `status: "open"` establishes that value even when it is omitted from each record. A complete filtered result still does not establish the whole unfiltered collection. Filtering may reduce returned data without reducing a server's scan or computation. Only an explicit backend work model can account for that difference.

`load` is your HTTP transport. `TaskPage.complete` reports whether the service established the final collection, including any partial-service failures. Vem accumulates page identities and keeps membership incomplete while continuation remains. A missing cursor is not, by itself, proof of completeness. Repeated cursors and page limits stop acquisition with an explanation; partial rows stay useful.

Pages may have different disclosure permissions. The accumulated collection is complete only while every contributing page’s evidence remains permitted; withdrawing a page’s permission preserves independently readable facts but removes that complete-set claim. Continuity combines across pages too: a complete set relies on every contributing page’s change coverage, while individual identities retain their own page’s support.

## Prerequisites and partial answers

Some reads require information first: for example, service capabilities determine which task representation exists. Declare that requirement with `readPrerequisites`:

<Example file="integration/planning.ts" region="read-prerequisites" />

Install this as `readPrerequisites: taskReadPrerequisites` and register a `service` definition whose sources supply `features`. Vem shares that prerequisite acquisition across consumers, then chooses task sources from the updated knowledge. Already satisfied task queries keep using their data; this declaration does not introduce verification on each read. Failed, denied, or still-incomplete prerequisites settle with an explanation instead of dispatching the guarded source or retrying indefinitely.

Use `fieldDependencies` when a derived value needs other fields or related resources. These supply an alternative way to obtain a value, alongside sources that return it directly. It returns descriptions of the required information, using known identities or relationships; it does not fetch or choose endpoints. Vem includes those prerequisites in the shared plan and reevaluates them as evidence arrives. The existing `derive` function computes the value and reports its evidence dependencies. See [relationships and derived values](/docs/data/connect/events).

A parent response can also establish another resource's existence or collection. Suppose a task detail includes its complete checklist. The checklist resource can declare a task-detail query through `membershipDependencies` for its list, or `presenceDependencies` for one item. Vem compares that route with direct checklist sources and can share a task read already needed elsewhere. The task response's extraction must still publish the checklist facts and scoped membership; a dependency declaration alone proves nothing. These callbacks return the same query or relationship descriptions as `fieldDependencies`, without orchestrating requests.

A source's declaration is a capability, not evidence. If a response omits fields or contains only part of a collection, publish exactly that. Vem can try another eligible source, then settles with the remaining gaps. It does not repeatedly request an unavailable field until it appears. Retry begins a new attempt; ordinary data has no time-based expiry.

## Classify a rejected read

A source normally throws an ordinary error when acquisition fails. If the backend establishes a more specific result, throw `AcquisitionError` from `@hyecompany/vem-data/runtime` with a `QueryIssue`, such as `{ kind: "access", message: "Listing is not permitted." }`. Consumers receive that classification alongside any still-readable content and can explicitly retry.

This describes the failed attempt. It does not revoke authentication, remove independently permitted facts, or permanently deny future attempts. Use the [access model](/docs/data/connect/access) separately when the backend provides evidence that disclosure permission has been withdrawn. Late classified failures use the same access-generation fence as other acquisition failures.
