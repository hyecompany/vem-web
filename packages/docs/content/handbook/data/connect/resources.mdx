A feature asks for tasks. Your integration describes the available backend reads and what each response provides. Vem chooses among them for the whole application’s outstanding needs.

This guide assumes a task API with two endpoints: `GET /api/tasks` returns **every task and all its fields**; `GET /api/tasks/:id` returns one task. A backend with pagination or brief list representations needs different coverage rules, explained below.

## Give features a contract

The contract names the fields, identity, commands, and editors that components can use. Constructing any of these descriptions performs no work.

The command and editor names are declarations; [their implementations](/docs/data/connect/commands-edits) come after the read adapter. Keep the contract in a module features can import. The HTTP adapter belongs in the owner, where credentials and transport are available.

<details>
<summary>Project scopes and advanced matching</summary>

Add `inScope` when a collection has project or tenant boundaries. A resource identity must distinguish otherwise identical names in different projects.

Most resources need no custom matcher. If your integration overrides equality matching with `matches`, it receives normalized equality maps, including equivalent `$and` conditions. List additional fields it reads in `queryDependencies` and return `"unknown"` when those inputs are absent. Vem evaluates the remaining normalized filter expressions itself.

</details>

Returning a batch lets the runtime apply it through the acquisition's context. For an intermediate update, use `context.observe(batch)`. Do not start a fetch and later call a global `runtime.observe`: that loses the request's protection against obsolete responses.

| Your response establishes… | Report… |
| --- | --- |
| Some fields of a task | A fact with those `values` |
| The tasks seen on one page | Membership with `complete: false` |
| The entire matching collection | Membership with `complete: true`, for its actual scope and filter |
| One task's details | Its facts; no claim about the whole collection |

Missing display fields keep a known task visible. Unknown filter fields keep a candidate unresolved unless other evidence, such as exact filtered membership, establishes the match. If a successful response cannot provide everything, return what it does establish; reads settle partial. Throw on an acquisition failure so the result can explain it and offer retry.

<details>
<summary>When omission means deletion</summary>

`replace` names a representation's fields whose omission means removal. A brief list response must not delete notes that only appear in details. Report `presence: "absent"` only when absence is established; a concealed resource or generic permission error does not prove deletion.

</details>

## Install the definition

Give `taskAdapter` to the owner's `resources` array and `taskRead` to the tab's read definitions. The [browser-host guide](/docs/data/connect/browser-host) shows that connection. Components continue importing `tasks` from the contract; adding a field does not add a fetch effect.

The [automatic planning guide](/docs/data/connect/planning) explains how these declarations combine across views and tabs, including costs, filters, and pages. For live updates, continue to [events](/docs/data/connect/events). For protected data, [connect permissions](/docs/data/connect/access).
