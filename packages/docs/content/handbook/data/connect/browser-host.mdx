This is application setup. Once it is in place, feature components only use the resource contract and hooks.

The **tab** renders UI. A **SharedWorker** runs the domain definitions, makes requests, receives events, and owns shared data. Both use the same pure read rules so filtering already-known data is immediate.

## 2. Start the owner

The worker imports the assembled owner definition as `taskDefinition`. This runnable task service emits full task updates on `task-events`; its facts declare that matching channel. Start with [resource sources](/docs/data/connect/resources), then add the event decoder and [commands and edits](/docs/data/connect/commands-edits) your backend supports. The shared compatibility object is the one above:

<Example file="task-board/owner.ts" region="owner" />

`/api/events` is this example's backend event stream. Adapt its URL and event decoder to your service. This fixture sends full task updates. `setContinuity` reports whether that channel is continuously delivering them; a normal incoming update goes through `client.event`.

The starter waits for the initial event connection to open or fail before admitting readers. This keeps a late startup coverage change from making the first request obsolete. On failure, readers can still acquire snapshots. Reconnecting does not make observations from the uncovered interval current; affected active consumers need new evidence. Give the event transport a connection deadline if it can remain silent indefinitely.

Publish the worker at a stable URL, such as `/task-owner.js`, and keep the lock name stable across deployments. Changing the lock name for each release could allow two owners to run at once.

## 3. Connect the tab and provide the client

Pass the same `taskRead` rules used by the owner. `ownerModule` is the URL of the compiled worker module, served from the application's origin.

<Example file="host-guide/browser.tsx" region="connect" />

Create the client once in the application entry point, then pass it into this provider. The browser needs HTTPS or loopback, SharedWorker, and Web Locks. Connection failures are application-level errors, separate from an individual query's failure.

A slow worker download, owner-lock wait, or host initialization keeps `connectionSnapshot().phase` at `connecting`. Elapsed time alone does not fail the connection; a late owner can still become ready. Worker errors, rejected initialization, and incompatible versions report an actual failure. Keep the application's connecting state visible, and let users reconnect or leave. An imperative read can stop waiting through its `AbortSignal` without closing the shared client. The host waits for the owner client's optional `ready` promise and delivers its initial knowledge snapshot before admitting queued demand. Restored rows can therefore supply nested consumers before their requirements are planned together. Give backend operations their own documented deadlines; the client handshake does not infer one.

<Example file="host-guide/browser.tsx" region="provider" />

Put your routes inside the provider. Close the client when the app is permanently disposed; do not recreate it on route changes.

## Decide what survives a restart

Storage is optional: omit `persistence` for an in-memory owner. With `DexiePersistence`, a definition's `persist` decides which fields can be saved. For example, the task definition allows `$presence`, `title`, and `status`, and leaves private notes out. Relationships have a separate `persistRelationship` allowance. The starter uses the explicit IndexedDB name `vem-data:task-board:v1`; the constructor uses that name directly. Choose a namespace your application owns.

`runtime.ready` means restoration was attempted. Establish the current caller through [access decisions](/docs/data/connect/access); storage must not choose the caller. Until then, protected saved data stays quarantined. Identifying the same caller resumes saved permissions and exposes supported stale values immediately, so mounted consumers can express their current needs together. Acquiring fresh values does not require clearing readable old ones.

`DexiePersistence` retains permission snapshots for up to 16 caller contexts; evicted snapshots require new permission evidence. The storage format upgrades automatically. Report persistence errors through `RuntimeOptions.onError`, and inspect `action.recovery` before promising restart recovery.

## Let the browser continue an upload

This optional host integration uses Background Fetch where available. Commands declare their HTTP transfer; feature components keep using `useCommand` and `useAction`. Configure three cooperating pieces once per application:

| Where | Responsibility |
| --- | --- |
| SharedWorker | Runs the action, prepares the request, and interprets its result |
| Page | Initiates the browser transfer after the ServiceWorker admits the handoff |
| ServiceWorker | Atomically claims the protected action and stores its completion receipt |

Serve this worker from your own origin with an appropriate scope. The example uses the origin root; an application under a subpath should use that subpath for both URL and scope. If the application already registers a ServiceWorker, install the handlers in that worker instead of creating a competing registration. This integration does not install a cache or intercept ordinary requests.

The native host accepts HTTP `POST`, `PUT`, and `PATCH` uploads with a `Blob` body and a small text response. The [transfer definition](/docs/data/connect/commands-edits#declare-an-http-upload) describes the backend contract. Browser support, storage, and permission can prevent handoff; display the action's actual [execution lifetime](/docs/data/understand/recovery#uploads-and-background-transfers), not a promise inferred from API availability.
